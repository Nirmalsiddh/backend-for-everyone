# Local operator dashboard

This dashboard makes the existing Fastify management API usable from a browser. It is **local single-operator mode**. Do not publicly expose it. Every management action uses the one configured backend owner. Final platform-user authentication will replace this temporary mechanism later.

## Run locally

Use Node.js 24 LTS. Set up backend migrations and bootstrap a platform user as described in the repository README, then run:

```sh
cd backend
npm ci
cp .env.example .env
# Configure .env, migrate, and bootstrap the configured owner first.
npm run db:migrate
npm run dev
```

In a separate terminal:

```sh
cd frontend
npm ci
cp .env.example .env.local
# Set BACKEND_ORIGIN and the same MANAGEMENT_API_TOKEN as backend.
npm run dev
```

Open http://127.0.0.1:3001/projects. Both development commands bind to loopback. For a local production build use `npm run build` followed by `npm start`.

Frontend server environment:

| Variable | Meaning |
| --- | --- |
| `BACKEND_ORIGIN` | Fixed Fastify origin, normally `http://127.0.0.1:3000`; no trailing slash, path, query, or embedded credentials |
| `MANAGEMENT_API_TOKEN` | Same temporary token as backend; server-only, never prefixed `NEXT_PUBLIC_` |
| `DASHBOARD_ALLOWED_HOSTS` | Exact permitted dashboard host:port list; defaults to local development/test hosts. Not user authentication |

The backend separately needs `PLATFORM_DATABASE_URL`, `MANAGEMENT_USER_ID`, and `CONNECTION_ENCRYPTION_KEY`; see `backend/.env.example`. Never put the encryption key or platform database URL in frontend configuration.

## Architecture

App Router pages use TanStack Query for management data and React Hook Form for editable forms. Zod checks frontend input for usability; Fastify remains authoritative. CSS supplies simple shared controls. No browser persistence is used for forms, runtime credentials, or secrets.

`src/lib/server/adapter.ts` maps explicitly supported routes and methods to a fixed backend origin. `/api/management/*` adds the operator token on the server. `/api/runtime/*` forwards only an explicitly supplied runtime bearer credential. Mutation requests require matching Origin and Host and reject cross-site fetches. Both adapters disable caching and preserve status and request IDs. Management responses use explicit safe DTOs and omit internal catalogs. The adapters do not perform database or product business logic.

Runtime base path on Fastify is `/api/{project-slug}`. The dashboard playground relay is `/api/runtime/{project-slug}` on the dashboard origin. Use the Fastify origin for integrating a separate application; relay success does not verify browser CORS configuration.

Schema previews are generated by the backend. Schema defaults may intentionally appear in generated DDL, so do not put secrets in defaults. Applied schema fields are immutable; only nullable columns without defaults or uniqueness may be added. Unknown apply/provision outcomes require operator review and are never automatically retried.

Workflow query means query by record ID. Workflow values are typed literals or structural references, never code. Conditions use nested Then/Else lists, with prior outputs scoped to their execution branch. The editor supports 30 total steps, 10 DB operations, 5 tables and condition nesting depth 3. Every path must end with a response. Publication snapshots and editable drafts are separate. The owned workflow GET response includes the published definition, so the editor compares it with the current draft after reload and during editing. Preview and publish operate on saved revisions and dependency hashes.

## Complete manual demo

Use a disposable customer PostgreSQL database and an existing schema. These actions create real tables and rows.

1. Create a project, then connect PostgreSQL. Saving tests the candidate credentials. Retest the saved connection. The password clears after submission.
2. Create `products` with required text `title` and optional UUID `owner_id`. Save the draft, preview generated SQL, then apply. The UUID `id` primary key is automatic.
3. On APIs, enable all five operations with `key_only` policies and save.
4. Generate a `read_write` API key. Copy it before closing the secret dialog. It cannot be recovered from the key list.
5. In Playground choose POST products, select API key credentials, paste the key, and send `{"title":"Initial product"}`. Inspect status, JSON, and request ID. Use list/get/PATCH/delete as needed.
6. On Authentication enable project auth and signup, save, then provision auth tables. Wait for `ready`.
7. In Playground use signup twice with separate emails and passwords of at least 15 characters. Use login to activate the session in memory, then send requests. Log in again to switch identities; tokens are not displayed or persisted.
8. On APIs change create/get/update/delete/list to `owner`, choose `owner_id`, and save. As Alice create a product without supplying `owner_id`; ownership is assigned by the backend. As Bob verify get/PATCH/delete of Alice’s ID return 404 and list excludes Alice’s rows. A known user UUID can be promoted on Authentication to test `allowAdmin` explicitly.
9. To inspect the workflow transaction with an API key, change list back to `key_only`.
10. Create POST workflow `accept-order`. Add required boolean input `accept`. Add an insert before the terminal response (the default Add step action inserts before it) into products, policy `key_only`, set title to a literal such as `Workflow committed`. Replace the final response with a condition comparing request input `accept` with boolean `true`. Set Then response to 201 and Else response to 422. Each branch can keep an empty object response. The insert must precede the condition.
11. Save draft, preview, publish, then enable. In Playground use the API key and call the workflow with `{"accept":true}`; a product is committed. Call with `{"accept":false}`; response is 422 and the preceding insert is rolled back. Compare product lists before and after.
12. Revoke the API key and verify a key-authenticated request returns 401. Disable the workflow, switch to a valid application-session credential, and verify the workflow path returns 404.
13. Reload pages. Saved projects, connection metadata, tables, policies, key metadata and workflows remain. Database passwords, full generated keys, and playground credentials do not reappear.

## Validation

```sh
npm run typecheck
npm test
npm run build
npx playwright install chromium
```

The E2E harness starts real backend and dashboard servers on 3010/3011. It requires two explicit, distinct **local disposable** database URLs with names matching `dashboard_e2e_*_test`. It rejects other hostnames/names. Do not point it at a development or production database. The role must be able to apply platform migrations and create customer schemas.

```sh
E2E_PLATFORM_DATABASE_URL=postgresql://USER:PASSWORD@127.0.0.1:5432/dashboard_e2e_platform_test \
E2E_CUSTOMER_DATABASE_URL=postgresql://USER:PASSWORD@127.0.0.1:5432/dashboard_e2e_customer_test \
npm run test:e2e
```

Backend dependencies must be installed too. The harness applies existing migrations, inserts a fixed test operator, generates temporary credentials, and creates a fresh customer schema each run. It does not alter backend `.env`. Test data remains in these disposable databases for inspection; drop the dedicated databases after use. Screenshots on failure contain test data; tracing is disabled to avoid storing request credentials. Unit tests cover DTO redaction, proxy credential separation, route restrictions, precision-preserving schema conversion and workflow references. The browser test exercises the full demo, including ownership, commit/rollback, revocation, disabling, persistence and secret absence.


## External tester boundary and reliability

The server-side management token is **not dashboard-user authentication**. Everyone who reaches the dashboard can act as the configured management owner. Keep both processes on loopback. For early external evaluation, prefer separate local installations with dedicated disposable databases, or put the dashboard behind an authenticated private access gateway/VPN with an explicit tester allowlist. Restrict direct access to Fastify management routes too. Set `DASHBOARD_ALLOWED_HOSTS` to the exact gateway host and port, terminate HTTPS at the trusted gateway, and validate the deployment's Host/Origin behavior. Do not share a publicly accessible unauthenticated URL. This milestone does not implement production platform login or multi-tenant operator identity.

Use disposable/test customer databases and restricted PostgreSQL roles. Connection checks establish connectivity and schema existence only, not every future DDL/CRUD permission. Safe identity and replacement blockers are available through owned connection GET. A previous successful check is historical evidence, not a current health guarantee. Schema/auth/workflow dependencies can block connection replacement; the dashboard does not rebind them.

Disabling SSL makes DB transport unencrypted. Destination/DNS and network-egress hardening remain deferred; only trusted operators may choose connection hosts. Authentication attempt counters are process-local, reset on restart, and see the dashboard relay as a shared client IP. They are not distributed production controls. There is no password reset or email verification. Use HTTPS for remote access; do not enter production credentials during usability testing.

API-key secrets appear once in a modal dialog with clipboard-error recovery. Login tokens are retained only in transient credential state; responses show safe user information and expiry. Credentials are cleared on logout, reload, and explicit clearing. Late responses are invalidated when clearing or changing target/credential mode. Copying, browser tooling, and screenshots may retain intentional secrets outside the app's state. Failed-test screenshots contain disposable test data; keep artifacts private.

Browser request cancellation stops waiting; it does not prove a submitted write was rolled back. Unknown write/apply/provision outcomes require operator review. Mutations are never automatically replayed. Relevant metadata refreshes on success and failure without discarding edits. The latest schema apply status is safe metadata; no catalog snapshots or raw migration definitions are exposed.

Dirty editors protect sidebar/project navigation with Save/Discard/Stay where a save callback is available; other forms offer Discard/Stay. Browser reload/close uses the browser's standard confirmation. Background refetch does not remount dirty editors. Conflicts preserve input; reload is an explicit discard action.

Workflow preview describes effective capabilities: touched tables, reads/writes, owner restrictions, admin bypass and applied-schema dependencies. Workflow permissions are independent of generic CRUD policies. Publishing an enabled workflow replaces its live version immediately. Error-status responses roll back preceding database writes. Stale schema dependencies block execution and require deliberate preview/republish.

## Performance follow-up (measure before optimizing)

- Customer database work uses fresh connections and repeated catalog checks.
- Schema lists perform per-table metadata/status reads.
- Workflow lists include full definitions and readiness reads; runtime still performs broad schema inspection.
- Recursive workflow editing rerenders nested form controls.
- Auth attempt counters are bounded in-process maps.

Record latency, query counts and memory with representative projects before adding pools, caches, workers or another state framework. No architectural optimization is included here.
